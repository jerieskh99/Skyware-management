01 - Triggering symptom

"Unknown field kind for select statement on model KnowledgeArticle"

Reported on the running dev server right after Knowledge V1 was merged to team1. The page /knowledge 500'd on every load.

What user saw

  • Knowledge list page returned a 500.
  • Sidebar badge endpoint 500'd similarly with "pending_review" expected KnowledgeArticleStatus".
  • All tests passed in CI (748/748).
  • Typecheck + lint green.

What was actually wrong

  • Prisma client expected new columns + enum values.
  • Live dev database lacked them entirely.
  • Migrations existed as files in worktree disks.
  • Not a single migration SQL file was tracked by git.
  • .gitignore line 20 had been silently dropping every migration since the initial commit.
02 - Root cause

One line in .gitignore. Every migration. Every phase.

The offending rule

# Prisma
prisma/migrations/**/migration.sql

Present since commit 649d811 (the very first commit). Effect: every migration.sql file written by every agent across Phase 1, 2, 3, 4, and Knowledge P1 was silently ignored. None tracked. None deployable to production.

Why CI did not catch it

  • All "integration" tests mock Prisma. No test ever connects to the live DB. So missing columns at runtime do not appear in test runs.
  • CI sets DATABASE_URL but never connects to it. The Postgres service container in verify job sits idle.
  • E2E job has continue-on-error: true. Even if it failed, it would not block a merge.
  • git ls-files prisma/migrations returned only the lock file. But nobody ran it.
03 - The fix that landed

Two-line gitignore patch. One consolidated migration. All tests green.

Step 1: gitignore

Removed line 20. Replaced with a comment explaining why migration files MUST be tracked. Production deploys now run prisma migrate deploy deterministically.

Step 2: track existing

4 migrations already on disk locally (init + mig1 + mig2 + mig3, generated by the user). Added to git tracking.

Step 3: consolidate Knowledge V1

Generated 20260527203406_knowledge_v1_apply via prisma migrate dev --create-only. 145 lines. Captures every Knowledge V1 schema delta. Applied via prisma migrate deploy.

Result: Commit 0f4510e on team1. Pushed to origin/team1. Dev DB now in sync with Prisma client. /knowledge stops 500-ing.

10 - CI improvements to prevent recurrence

5 changes that would have caught the bug.

  1. Add pnpm exec prisma migrate deploy to the verify job before pnpm test. Would have failed loudly: "no migrations to apply" on a fresh service Postgres.
  2. Add prisma migrate status check. Fail the job if status is not "Database schema is up to date".
  3. Promote the e2e job to blocking (continue-on-error: false) and add a spec that fetches /knowledge and asserts non-500 response. Direct catch for the original symptom.
  4. Add pre-commit hook that warns on untracked prisma/migrations/**/migration.sql files. Catches the regression at the workstation.
  5. Add an agent-written-file safety sweep: diff disk-vs-git for any new file under prisma/migrations/. Generalizes beyond Prisma to catch any future .gitignore swallow.
