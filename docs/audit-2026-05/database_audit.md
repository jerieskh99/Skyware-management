# Database Audit — Skyware Management Portal MVP

Auditor: Senior Data Engineer
Date: 2026-05-24
Scope: `prisma/schema.prisma`, `prisma/seed.ts`, `prisma/fixtures/`, `prisma/migrations/`, `lib/*` Prisma query patterns, intended-vs-actual data model gap.
Method: full file review. No code changes.

---

## 1. Executive Summary

The most serious finding in this audit is structural and immediate. The Prisma schema at `prisma/schema.prisma` (812 lines, 35 models) has never been baselined as a migration. `prisma/migrations/` contains only `migration_lock.toml` and no SQL migration directories. Every developer and every environment is therefore relying on `prisma db push` (or an unrecorded ad-hoc apply) to materialize the schema. This is acceptable for solo experimentation but is incompatible with the pilot launch documented in `docs/pilot-launch-checklist.md` and `docs/phase-10-hardening-audit.md` Section 10, both of which presume a deployable, restorable database.

The phase-10 audit reports `pnpm exec prisma migrate status` returning "Up to date" (line 246). That status is misleading because there are no migrations to be up-to-date with. `migrate status` against an empty `_prisma_migrations` directory will report no pending migrations, which is technically correct but does not mean the database matches the schema.

Beyond the migration gap, the schema itself is in good shape for an MVP. Naming is consistent. Foreign keys are present. Soft-delete is not used (deletion semantics rely on FK behavior, which defaults to RESTRICT in Prisma and is therefore safe-by-default but needs explicit review). Most hot paths have at least one index, and `lib/*` queries use a transaction-per-mutation pattern that correctly wraps `writeAudit()`. The seed file is small, idempotent, and intentionally placeholder-only.

The main schema-level concerns are:

1. Money is stored as plain `Int` minor units with no domain wrapper and no `Decimal` validation. Two payment-source FKs are nullable polymorphism without a check constraint. Receipt VAT math fields are nullable but read by the UI as if non-null.
2. Several FKs have no explicit `onDelete` declared and inherit Prisma's default RESTRICT. This is correct for most relations but means an admin attempting to delete a `Client`, `User`, or `Department` will hit obscure 500 errors from the database rather than a friendly 4xx.
3. There are no partial indexes despite the spec calling for one on `TimeSession (user_id) WHERE ended_at IS NULL`. The Prisma 5 schema syntax does not natively support partial indexes; this gap will need raw SQL once migrations begin.
4. Full-text search is implied by `lib/jobs/queries.ts` and `lib/communication/queries.ts` (both use `contains` + `mode: "insensitive"` against `Job.title`, `Job.description`, `CommunicationPost.title`, `CommunicationPost.body`). Without `pg_trgm` or `tsvector` indexes these scans become sequential as data grows. The final-plan doc Section 9 explicitly calls for FTS indexes.
5. The `Notification` model promoted to MVP in `docs/internal-management-portal-enhancement/08-data-model-additions.md` Section 1.5 is not present in the schema. The User relation `notifications` is missing entirely.

Top three data risks are listed in the Handoff to PM at the end of this document.

## 2. Migration State

### 2.1 Current state — confirmed

Listing `prisma/migrations/` returns one file:

```
prisma/migrations/migration_lock.toml
```

Contents:

```
# Please do not edit this file manually
# It should be added in your version-control system (i.e. Git)
provider = "postgresql"
```

There are no `YYYYMMDDHHMMSS_name/` subdirectories. There has never been a `prisma migrate dev` or `prisma migrate deploy` against this project.

The schema has been built up to 812 lines, 35 models, 22 enums. The shape of `prisma/seed.ts` (uses generated Prisma types and the runtime client) means the schema is being applied somehow at dev time, almost certainly via `prisma db push`. The phase-10 audit report at `docs/phase-10-hardening-audit.md` line 246 reads `pnpm exec prisma migrate status` → "Up to date", which is the behavior of `migrate status` when no migrations exist: there are no pending migrations because there are no migrations at all.

### 2.2 Implications

#### For local development branches
- `db push` mode means schema and database can silently diverge. Switching branches drops or creates tables without informing the developer in a reviewable way.
- There is no replayable history. A new contributor has no record of how the schema reached its current form.
- Two developers working in parallel on different schema edits cannot merge those edits as ordered migrations; they merge two `schema.prisma` files and re-push.

#### For the pilot launch
- `docs/pilot-launch-checklist.md` and `docs/phase-10-hardening-audit.md` Section 10 item 5 explicitly call for "production PostgreSQL with automated backups." A production database must be initialized by a deterministic, reviewable migration. `db push` is not that.
- The very first deploy will need to either (a) baseline the existing schema as a single squashed initial migration, then deploy it, or (b) `db push --skip-generate` against a fresh prod DB, accepting that destructive deploys later cannot be audited.
- The pilot should never see option (b). Choose (a).

#### For production after pilot
- Without migrations, there is no rollback story. A bad schema change cannot be reverted with `prisma migrate resolve --rolled-back`. The DBA's only tool would be `pg_restore` from a backup.
- Any data-bearing schema change (rename a column, change a type, add a NOT NULL with default) cannot be expressed at the level needed for safe production deployment. Prisma's `db push` does not generate data-migration SQL.

### 2.3 Required steps to baseline

The Prisma documentation prescribes a clear path: `prisma migrate diff` to produce SQL, then `prisma migrate resolve --applied <name>` to mark it applied on every existing environment. The audit does not perform this work, only specifies it.

Suggested sequence, for the team to execute as a separate PR:

1. Stop all schema edits for the duration of the baseline.
2. Run `pnpm exec prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` to produce a single SQL script.
3. Save it under `prisma/migrations/20260524000000_init/migration.sql`.
4. On any existing database that already matches the schema (dev, staging if it exists), run `pnpm exec prisma migrate resolve --applied 20260524000000_init` to mark this migration as already applied without re-running it.
5. On fresh databases, `pnpm exec prisma migrate deploy` will run the migration normally.
6. From this point forward, all schema edits go through `pnpm exec prisma migrate dev --name <change>` to generate an incremental migration.

Steps 4 and 6 are the critical operational changes. They turn `db push` into `migrate dev`, which is the supported production workflow.

## 3. Schema Review — per entity group

### 3.1 Identity and access

Entities: `Department`, `Role`, `User`.

`Department` (`prisma/schema.prisma:178-193`) uses a `DepartmentKey` enum (`global`, `helpdesk`, `it`, `rnd`) and stores both `name_en` and `name_he`. The enum-plus-lookup hybrid is appropriate: the enum prevents typos in code, the row stores translatable labels. `isGlobal` is denormalized from `key == 'global'`; this is unnecessary but not harmful.

`Role` (`prisma/schema.prisma:195-208`) follows the same pattern with `RoleKey` (`employee`, `ceo`, `cto`). Three rows. The `isAdmin` flag is the only behavioral hint and is used in `lib/permissions.ts`.

`User` (`prisma/schema.prisma:210-249`) holds `passwordHash`, `displayName`, `username`, `email`. The `timezone` defaults to `"Asia/Jerusalem"`; the `languagePref` defaults to `en`. Both are appropriate for a Jerusalem-based MSP. `lastLoginAt` is nullable and updated by NextAuth.

Observations:

- `username` and `email` are both `@unique`. Good.
- No `avatar_attachment_id` field, although `docs/internal-management-portal-final-plan/03-data-model-final.md` line 102 calls for it. Minor delta. Phase 2.
- `User` has a long fan-out: 18 relations including `assignedJobs`, `createdJobs`, `statusEvents`, `submittedReports`, `approvedReports`, `timeSessions`, `posts`, `replies`, `savedViewsOwned`, `savedViewsCreated`, `auditLogs`, `environmentNotes`, `createdClients`, `createdPayments`, `finalizedReceipts`, `uploadedAttachments`, `bankUsagesRecorded`, `updatedFeatureFlags`. All these FKs default to RESTRICT. A deactivated user cannot be deleted (and should not be). Acceptable; just be explicit in any future admin "delete user" UI that it is hard-blocked.

### 3.2 Clients

Entities: `Client`, `BillingAccount`, `ClientEnvironmentNote`.

`Client` (`prisma/schema.prisma:405-432`) has `companyName`, `contactPerson`, `email`, `phone`, `address`, `israeliTaxId`, `status`, `notes`, `createdByUserId`. Two indexes: `companyName` and `status`.

`israeliTaxId` is `String?` with no unique constraint. The final-plan doc Section 3.11 line 219 explicitly recommends `unique-if-present(israeli_tax_id)`. Without this, two `Client` rows can share the same tax ID, which a tax invoice would reference incorrectly. **Gap.**

`BillingAccount` (`prisma/schema.prisma:434-449`) has `clientId @unique` and a `defaultCurrency`. This is correct 1:1.

`ClientEnvironmentNote` (`prisma/schema.prisma:451-466`) has `section` enum, `content`, and the editor stamp. Index on `(clientId, section)` is right.

### 3.3 Jobs and time

Entities: `Job`, `JobStatusEvent`, `WorkReport`, `TimeSession`, `Tag`, `JobTag`.

`Job` (`prisma/schema.prisma:251-302`) is the central entity. Six indexes are declared:

- `(departmentId, status)` — used by `lib/dashboard/queries.ts` admin KPIs and `lib/statistics/queries.ts` department breakdown.
- `(assignedEmployeeId, status)` — used by `lib/dashboard/queries.ts` employee KPIs and lists.
- `(clientId)` — used by `lib/clients/queries.ts` `getClientJobs()`.
- `(status, createdAt DESC)` — used by hub listing (`app/api/hub/[scope]/route.ts`) and active-job sorts.
- `(priority, status)` — used by `lib/jobs/queries.ts` sort order `[priority desc, createdAt desc]`.
- `(severity, status)` — defensive.

Timestamps: every status transition stamps a dedicated column (`assignedTimestamp`, `takenTimestamp`, `startedTimestamp`, `completedTimestamp`, `reviewedTimestamp`, `cancelledTimestamp`, `firstResponseAt`). Plus generic `createdAt`/`updatedAt`. This is denormalized but matches the spec's intent (`docs/internal-management-portal-final-plan/03-data-model-final.md:136`) and powers the `getOverviewKpis` aggregations in `lib/statistics/queries.ts:30-90`.

Concern: `timeSpentMinutes` is a cached `Int` updated by `app/api/jobs/[id]/work-report/route.ts:69` when a work report is submitted. There is no reconciliation between this cache and the sum of `TimeSession.accumulatedMinutes` for the job. If an employee corrects a timer after submission, the two views disagree. **Acceptable for MVP; flag for Phase 2.**

`JobStatusEvent` (`prisma/schema.prisma:304-321`) is append-only. Indexes on `(jobId, changedAt DESC)` and `(changedByUserId, changedAt DESC)` are right. `reopened` boolean is set by `app/api/jobs/[id]/transitions/route.ts:46` via `lib/jobs/lifecycle.ts::isReopening()`.

`WorkReport` (`prisma/schema.prisma:323-342`) has `@unique` on `jobId`, enforcing 1:1. Note the `upsert` pattern in `app/api/jobs/[id]/work-report/route.ts:45` allows the assignee to re-submit, overwriting in place. There is no historical record of prior submissions; the AuditLog captures the new value but not the previous body. **Minor gap.** Consider keeping a `WorkReportRevision` table or storing the old summary in AuditLog `diff_json`.

`TimeSession` (`prisma/schema.prisma:344-363`) holds `startedAt`, `pausedAt`, `resumedAt`, `endedAt`, `accumulatedMinutes`. Only one index: `(jobId, startedAt DESC)`. Missing: the spec calls for a partial index on `(user_id)` where `ended_at IS NULL`. This is what `app/api/jobs/[id]/time-sessions/route.ts:41` uses to "end any existing active session for this user" via `updateMany({ where: { userId, endedAt: null } })`. Today that scan walks the user's entire session history. **Index gap, see Section 6.**

`Tag`, `JobTag`, `PostTag` (`prisma/schema.prisma:365-403`) are clean. The two join tables correctly use composite primary keys and `onDelete: Cascade`.

### 3.4 Billing and payments

Entities: `MonthlyBillingItem`, `HourlyBank`, `HourlyBankUsage`, `OneTimeJobCharge`, `Payment`.

`MonthlyBillingItem` (`prisma/schema.prisma:468-491`) uses `@db.Date` for `startDate`, `endDate`, `nextDueDate`. Good. Three indexes. Price is `priceAmountPlaceholder Int?` (nullable). The field name carries `Placeholder` which is intentional — the spec is explicit that real prices are not seeded.

`HourlyBank` (`prisma/schema.prisma:493-515`) has `totalHoursPurchasedMinutes Int?` (yes, the naming is confusing — minutes stored in a field with `Hours` in the name; this should be either renamed or removed before pilot). Same for `pricePerHourPlaceholder` and `totalPaymentPlaceholder`. All `Int?`.

`HourlyBankUsage` (`prisma/schema.prisma:517-535`) is correct. Indexes on `(hourlyBankId, usedAt DESC)` and `(jobId)`. There is **no validation that `minutesUsed > 0`**; the final-plan doc Section 3.16 explicitly requires this. Today the API enforces it at the Zod layer (`app/api/clients/[id]/billing/hourly-banks/[bankId]/usages/route.ts:38` uses `.positive()`), but the database accepts any integer including negatives. A check constraint should be added.

`OneTimeJobCharge` (`prisma/schema.prisma:537-556`) has `jobId @unique`. Good — one charge per job. Has a snapshot `jobNameSnapshot` to preserve job title at the time of charge. Good design. Indexes: none on `(billingAccountId)` despite the final-plan doc Section 3.17 calling for it. **Gap.**

`Payment` (`prisma/schema.prisma:558-592`) carries `sourceType` enum (`monthly`, `hourly_bank`, `one_time`) plus two nullable FKs (`sourceMonthlyId`, `sourceHourlyId`). For `one_time`, the reverse relation lives in `OneTimeJobCharge.paymentId`. This is workable but **the integrity is application-enforced, not database-enforced**: nothing prevents inserting a `Payment` with `sourceType = 'monthly'` and both source FKs null, or both set. Add a check constraint:

```
CHECK (
  (source_type = 'monthly' AND source_monthly_id IS NOT NULL AND source_hourly_id IS NULL)
  OR (source_type = 'hourly_bank' AND source_hourly_id IS NOT NULL AND source_monthly_id IS NULL)
  OR (source_type = 'one_time' AND source_monthly_id IS NULL AND source_hourly_id IS NULL)
)
```

This is a raw-SQL addition (Prisma 5 does not generate check constraints natively). Schedule it with the partial-index work.

Indexes: `(clientId, status)`, `(status, dueDate)`, `(paidDate)`. All used by `lib/billing/queries.ts:90-100` (`getAgingPayments`) and `lib/billing/queries.ts:60-78` (`getBillingKpis`).

`amountPlaceholder Int?` is nullable. The API at `app/api/billing/payments/[id]/route.ts:49-51` requires `paidDate` when transitioning to `paid` but does **not** require an amount. A finalized payment with `amountPlaceholder = NULL` is structurally allowed. **Real-money concern; see Section 4.**

### 3.5 Documents (receipts and tax docs)

Entities: `ReceiptDocument`, `ReceiptDocumentSequence`.

`ReceiptDocument` (`prisma/schema.prisma:594-632`) carries six document types (`invoice`, `receipt`, `tax_invoice`, `tax_invoice_receipt`, `credit_note`, `proforma_invoice`), three statuses (`draft`, `finalized`, `cancelled`), and the Israeli tax-authority allocation lifecycle (`allocationNumber`, `allocationStatus`, `allocationObtainedAt`).

Strong points:

- Money is stored as integer minor units. VAT rate stored as basis points (`vatRateBasisPoints Int default 1800` means 18.00 percent). Good.
- The composite unique `(type, documentNumberYear, documentNumber)` (named `unique_document_number`) enforces no two finalized documents of the same type share a number within a year.
- A separate `ReceiptDocumentSequence` model with `unique(type, year)` exists for atomic next-number generation.

Concerns:

- `amountBeforeVat`, `vatAmount`, `totalAmount` are all `Int?` (nullable). For a finalized invoice, all three must be non-null and arithmetically consistent (`totalAmount = amountBeforeVat + vatAmount`). The schema does not enforce this. Application code does not enforce it either, because **there are no receipt API routes yet** (Phase 7 is a stub, confirmed in `docs/phase-10-hardening-audit.md` line 83). When Phase 7 lands, add a check constraint or split into two table states (`ReceiptDraft` vs `ReceiptFinalized`).
- The `descriptionLines` field is `Json @default("[]")` with no schema validation at the DB layer. The spec at line 319 expects each element to have `{description, quantity, unit_price, subtotal}`. Without Zod-level validation in code or check constraints, a malformed array could be persisted.
- `documentNumber` and `documentNumberYear` are nullable while in draft. This is correct, but the partial unique constraint should also reflect that — Prisma's `@@unique([type, documentNumberYear, documentNumber])` will accept multiple rows with `(type, null, null)`, since Postgres considers NULL values distinct in unique constraints. This is the intended behavior here (many drafts can co-exist with no number) and is fine. Worth documenting.
- `language` is `String @default("he")`. The spec line 328 expected an enum `(he, en, both)`. Storing as free-form string permits drift. Minor.

`ReceiptDocumentSequence` (`prisma/schema.prisma:634-644`) is a small "next-number" table. Critical that finalization uses `SELECT ... FOR UPDATE` inside a transaction; the spec explicitly requires this at line 344. Since no receipt API routes exist yet, this contract is unwritten. Make sure the Phase 7 PR includes that pattern explicitly.

### 3.6 Communication

Entities: `CommunicationChannel`, `CommunicationPost`, `CommunicationReply`.

`CommunicationChannel` (`prisma/schema.prisma:646-661`) uses `CommunicationChannelKey` enum and an optional `departmentId`. Good.

`CommunicationPost` (`prisma/schema.prisma:663-689`) carries `title`, `body @db.Text`, optional `relatedJobId`, optional `relatedClientId`, `pinned`, `resolved`. Two indexes: `(channelId, createdAt DESC)` and `(authorId)`. The final-plan doc Section 3.22 line 363 also calls for `full-text on title plus body`. **Missing.** `lib/communication/queries.ts:70-74` and `app/api/search/route.ts:105-108` use `contains` + `mode: "insensitive"` against both columns. With no FTS index this is a sequential scan. See Section 6.

`CommunicationReply` (`prisma/schema.prisma:691-706`) is minimal. Index `(postId, createdAt)` is correct (note: ASC not DESC since the UI renders chronologically — the query at `lib/communication/queries.ts:90` confirms ASC).

### 3.7 Saved views

Entity: `SavedView`.

`SavedView` (`prisma/schema.prisma:708-726`) carries `userId?`, `scope` enum, `name`, `filterJson Json`, `isTeam`. Indexes on `(userId, scope)` and `(isTeam, scope)`. Good.

Concern: `filterJson` is unstructured. The spec at line 575 of `08-data-model-additions.md` recommends Zod or JSON-Schema validation per scope. The schema cannot enforce this; application code should at write time.

### 3.8 Audit

Entity: `AuditLog`.

`AuditLog` (`prisma/schema.prisma:728-745`) carries `actorUserId?`, `action`, `entityType`, `entityId`, `diffJson?`, `ipAddress?`, `userAgent?`, `createdAt`. Three indexes: `(entityType, entityId, createdAt DESC)`, `(actorUserId, createdAt DESC)`, `(action, createdAt DESC)`. Good — matches spec section 3.25 indexes exactly.

The `lib/audit.ts:39-58` helper enforces transactional writes (`tx.auditLog.create`) and redacts a 12-field denylist. Strong design.

Concerns:

- `entityId` is typed `@db.Uuid`. This is correct for almost all entities but the `JobTag` and `PostTag` join tables use composite primary keys — they cannot be audited individually with this schema. Today they are not audited; that is appropriate.
- `action` is a free-form `String`. Spec section 6.2 lists action namespaces (`user.*`, `job.*`, etc.). Without an enum or a check constraint, typos like `pavment.created` go silently into the audit log and break filtered reads. A controlled vocabulary table (with FK) or a string enum is worth considering at Phase 2. For MVP, a unit-tested constants file would suffice.
- `AuditLog` is append-only by convention only — there is no DB-level prevention of UPDATE or DELETE. For a true audit log this should be enforced at the DB role/grant level in production.
- No retention/archival policy implemented. Spec section 6.3 says "indefinite at MVP" and "7-year retention policy applied at Phase 2 once accountant confirms." This is fine for now.

### 3.9 Notifications

**Not present.**

`docs/internal-management-portal-enhancement/08-data-model-additions.md` Section 1.5 explicitly promotes `Notification` to MVP with triggers `sla.breached`, `job.assigned`, `mention`. The model is described with fields `id, user_id, kind, title, body, link, read_at, entity_type, entity_id`.

The schema has no `Notification` model. `User` has no `notifications` relation. The repo has no notification API routes or queries. This is a documented intended-vs-actual gap. The phase-10 audit at line 270 lists "Phase 7 Receipts" and "CSP headers" as MVP gaps but does not list Notifications. The contradiction between the data-model addendum and the implementation should be reconciled by the PM before pilot.

## 4. Field-level Concerns

### 4.1 Money types

Every money field in `prisma/schema.prisma` is `Int` (minor units) and nullable:

- `MonthlyBillingItem.priceAmountPlaceholder Int?` (line 472)
- `HourlyBank.pricePerHourPlaceholder Int?` (line 497)
- `HourlyBank.totalPaymentPlaceholder Int?` (line 498)
- `HourlyBank.totalHoursPurchasedMinutes Int?` (line 496)
- `OneTimeJobCharge.priceAmountPlaceholder Int?` (line 542)
- `Payment.amountPlaceholder Int?` (line 564)
- `ReceiptDocument.amountBeforeVat Int?` (line 605)
- `ReceiptDocument.vatAmount Int?` (line 607)
- `ReceiptDocument.totalAmount Int?` (line 608)

Integer minor units is a defensible choice (it avoids floating-point error and matches the data-model spec). `Decimal(12,2)` would be slightly more readable but functionally equivalent. The choice is fine.

What is **not** fine:

1. Every money column is nullable. For a `Payment` in status `paid`, `amountPlaceholder` cannot be `NULL`. Today this is enforced only by sales etiquette, not by schema. **Add check constraints when Phase 7 / accountant lock-in happens.**
2. No currency is stored alongside placeholder amounts in `MonthlyBillingItem`, `HourlyBank`, `OneTimeJobCharge` — those fields do exist (`currency Currency @default(ILS)`), but the spec is explicit that all amounts must always be paired with their currency. Today they are. Good.
3. The `Placeholder` suffix is a code-level signal that these are sample numbers. When real money flows in, **the field name should be renamed** to avoid the implication that values are placeholders. A migration rename will be needed.

### 4.2 Timestamp / timezone handling

All `DateTime` fields use Prisma's default which maps to Postgres `timestamp(3)` (without timezone). Combined with `User.timezone @default("Asia/Jerusalem")` and `lib/time.ts` using `date-fns-tz` with `process.env["TZ"] ?? "Asia/Jerusalem"`, the model assumes:

- All timestamps in the database are UTC.
- Display logic converts to Asia/Jerusalem.
- The server's `TZ` env var should be set to `Asia/Jerusalem` (or kept UTC if the application layer handles all conversions).

This works but is brittle: if a future deploy runs in a container with `TZ=UTC` and `lib/time.ts` falls back to UTC for display, end-users will see UTC times in their UI. **Recommend pinning `TZ=Asia/Jerusalem` in production env explicitly** and adding a test.

`@db.Date` is used for `MonthlyBillingItem.startDate`, `endDate`, `nextDueDate`, `HourlyBank.purchaseDate`, `expiryDate`, `Payment.issuedDate`, `dueDate`, `paidDate`, `ReceiptDocument.issueDate`, `paymentDate`. This is correct: these are calendar dates, not timestamps, and should not shift across timezones.

### 4.3 Enum vs lookup tables

The schema uses Prisma enums extensively (`DepartmentKey`, `RoleKey`, `JobStatus`, `JobPriority`, `JobSeverity`, `JobSource`, `PaymentStatus`, `PaymentMethod`, `PaymentSourceType`, `ReceiptDocumentType`, `ReceiptDocumentStatus`, `AllocationStatus`, `ClientStatus`, `MonthlyBillingStatus`, `HourlyBankStatus`, `TagScope`, `AttachmentVisibility`, `CommunicationChannelKey`, `SavedViewScope`, `TimerSource`, `EnvironmentNoteSection`, `Currency`).

This is the right call for fixed, application-controlled vocabularies. Compared to lookup tables, enums:

- Are checked at the database level (Postgres `CREATE TYPE`).
- Cannot be modified outside a schema migration (which is good for control, bad for ops if a typo lands).
- Cannot easily store translations or display order.

The combination of `Department` and `Role` as lookup tables (keyed by an enum) plus the rest as pure enums is consistent with the final-plan doc and is fine.

One concern: adding a value to a Postgres enum requires `ALTER TYPE ... ADD VALUE` which **cannot run inside a transaction in some Postgres versions** and **cannot be removed once added**. Prisma's `migrate dev` handles this but the team should be aware. For very volatile vocabularies, prefer lookup tables.

### 4.4 Nullable choices

A spot check shows reasonable nullability:

- `Job.clientId` nullable — supports internal jobs without a client. Good.
- `Job.assignedEmployeeId` nullable — supports unassigned (hub) jobs. Good.
- `Job.linkedPaymentId` nullable — billing is optional per job. Good.
- `Client.email`, `phone`, `address`, `israeliTaxId` all nullable — appropriate for partial data entry.
- `JobStatusEvent.fromStatus` nullable — represents the creation event. Good (`prisma/schema.prisma:307`).
- `Payment.method` nullable — payments may not have a method until paid. Good.
- `ReceiptDocument.documentNumber`, `documentNumberYear` nullable — drafts have no number yet. Good.

Less appropriate:

- All money fields nullable (already discussed).
- `User.lastLoginAt` nullable — correct for users who have never logged in.
- `JobStatusEvent.note` nullable — correct.

### 4.5 Length constraints

Prisma's `String` maps to Postgres `text`, unbounded. Zod schemas in the API routes enforce maximum lengths (e.g., `Client.companyName` 200 chars in `app/api/clients/route.ts:31`, `Client.notes` 3000 chars), but the **database does not**. A misbehaving worker process or a bypass of the Zod layer can store arbitrarily large strings. For pilot scale this is acceptable. For production-grade hardening, consider `@db.VarChar(200)` where reasonable, especially on indexed columns (`Tag.key`, `User.username`, `User.email`, `Client.companyName`).

### 4.6 Hebrew / Unicode

Postgres `text` and `varchar` accept UTF-8 by default; no special collation work is required for Hebrew storage. The default collation is the database default, which is fine for substring search via `ILIKE` (used by `contains` + `mode: "insensitive"`).

Concerns:

- For Hebrew-language sorting (e.g., a future "sort clients A-Z" view applied to `companyName` that may contain Hebrew letters), the default collation may not sort Hebrew correctly. Consider `COLLATE "he_IL"` or `COLLATE "und-u-co-standard"` if this becomes a UX requirement.
- Full-text search on Hebrew is *not* covered by Postgres's `to_tsvector('english', ...)` out of the box. The team should pick `'simple'` or build a Hebrew dictionary before adding FTS indexes (see Section 6).
- All seeded labels in `prisma/fixtures/*.json` include Hebrew (`"דחוף"`, `"תקלת לקוח"`, etc.) and load cleanly via `prisma.tag.upsert` because Prisma transparently handles UTF-8.

## 5. Relationships and Cascades

### 5.1 Explicit cascade declarations

The schema declares `onDelete: Cascade` on three sets of pure join tables:

- `JobTag` (`prisma/schema.prisma:386-388`)
- `PostTag` (`prisma/schema.prisma:397-399`)
- `JobAttachment`, `PostAttachment`, `ReplyAttachment` (`prisma/schema.prisma:766-797`)

This is correct. When a `Job` is deleted, its `JobTag` rows are cleaned up automatically. The `Tag` itself is not affected.

### 5.2 Implicit RESTRICT everywhere else

Every other foreign key relies on Prisma's default `onDelete: NoAction` (translated by Prisma 5 to Postgres `NO ACTION`, which behaves like `RESTRICT` for most checks).

Implications:

- Deleting a `User` who has authored anything fails. This is appropriate (we keep history).
- Deleting a `Client` who has any `Job`, `Payment`, `BillingAccount`, `ReceiptDocument`, or `ClientEnvironmentNote` fails. Appropriate, but the UI must offer "deactivate" via `status = inactive` instead. Confirmed: `ClientStatus` enum exists and the `lib/clients/queries.ts` uses it.
- Deleting a `Department` fails if any user, job, or channel references it. Appropriate.
- Deleting a `Job` that has `JobStatusEvent`, `WorkReport`, `TimeSession`, `HourlyBankUsage`, `OneTimeJobCharge`, `CommunicationPost` (via `relatedJobId`) fails.
- Deleting a `Payment` that has `Job.linkedPaymentId` references fails. Appropriate; payments should never be hard-deleted.

The risk is the inverse: there is no admin "delete" UI for any of these entities, so the default RESTRICT is effectively unreachable. If a hard-delete UI is ever added, it will surface obscure 500 errors from the DB. **Recommend: never expose hard-delete in the UI; only "deactivate" / "archive" workflows.**

### 5.3 Orphan risks

- `OneTimeJobCharge.paymentId` is nullable and references `Payment`. There is no DB constraint linking the two beyond the FK. If a `Payment` is deleted (today impossible by RESTRICT), the charge would orphan. Today this is safe.
- `Job.linkedPaymentId` is nullable. Same scenario.
- `CommunicationPost.relatedJobId` and `relatedClientId` are both nullable references. If the related entity is deactivated (not deleted), the post still points to it. Reads need to handle the case gracefully. `lib/communication/queries.ts` does, via the `select`-only relation.

### 5.4 Polymorphic references

`AuditLog.entityId` is typed `@db.Uuid` but has no foreign key — it references many entity types via the `entityType` discriminator. This is the standard polymorphic-audit pattern. Acceptable.

`SavedView.userId` is nullable for team views — clean. `createdById` is non-null. Good.

`CommunicationPost.relatedJobId` / `relatedClientId` are two scalar FKs; only one would typically be set. There is no check constraint saying "at most one of these two is set." Probably fine at MVP.

### 6.2 Indexes that should be added

#### Active `TimeSession` per user (partial)

Used by `app/api/jobs/[id]/time-sessions/route.ts:41`:

```ts
await tx.timeSession.updateMany({
  where: { userId: user.id, endedAt: null },
  data: { endedAt: now },
});
```

This scans every `TimeSession` for the user. Spec section 3.7 explicitly calls for a partial index:

```sql
CREATE INDEX time_sessions_active_per_user
  ON time_sessions (user_id)
  WHERE ended_at IS NULL;
```

Prisma 5 does not support partial indexes natively. Add via raw SQL in the baseline migration.

#### Full-text on `Job.title`, `Job.description`

Used by `lib/jobs/queries.ts:152-157` and `app/api/search/route.ts:52-56`. Both do `contains` (translated to `ILIKE %q%`), which is a sequential scan.

Add (raw SQL):

```sql
CREATE INDEX jobs_title_trgm ON jobs USING gin (title gin_trgm_ops);
CREATE INDEX jobs_description_trgm ON jobs USING gin (description gin_trgm_ops);
```

Requires `CREATE EXTENSION pg_trgm;`. Alternatively use `tsvector`, but `pg_trgm` handles partial substring search transparently with `ILIKE`.

#### Full-text on `CommunicationPost.title`, `body`

Same rationale, used by `lib/communication/queries.ts:70-74` and `app/api/search/route.ts:105-108`.

#### Index `Client.companyName` for FTS

Used by `lib/clients/queries.ts:13` (`ILIKE`). Already has a B-tree index on `(companyName)`, but `ILIKE %q%` will not use a B-tree. Add `pg_trgm` GIN index.

#### Missing index on `OneTimeJobCharge.billingAccountId`

The spec calls for it (line 288). Currently only `jobId @unique` is indexed.

#### Missing partial unique index on `Client.israeliTaxId`

The spec calls for `unique-if-present`. Today no constraint exists. Two clients can share a tax ID.

```sql
CREATE UNIQUE INDEX clients_israeli_tax_id_unique
  ON clients (israeli_tax_id)
  WHERE israeli_tax_id IS NOT NULL;
```

### 6.3 Indexes that may be over-engineered

`Job (severity, status)` (line 300) is declared but no query in `lib/*` filters by severity alone. It is used as a secondary sort in `lib/jobs/queries.ts`. Not harmful; B-tree maintenance cost is small. Leave as-is for MVP.

- `app/api/clients/[id]/billing/hourly-banks/[bankId]/usages/route.ts:25-32` returns every usage for a bank.
- `app/api/clients/[id]/billing/monthly-items/route.ts:23-26` returns every monthly item.
- `app/api/clients/[id]/billing/one-time-charges/route.ts:23-29` returns every charge.
- `app/api/clients/[id]/environment-notes/route.ts` (need to confirm — not read in this audit but mentioned in `listVisibleChannels`).
- `app/api/hub/[scope]/route.ts:24-46` returns every available job in a hub.
- `app/api/admin/users/route.ts:15-27` returns every user.
- `app/api/users/route.ts:14-23` returns every user.
- `app/api/tags/route.ts:9-12` returns every tag.
- `app/api/channels/route.ts` likely returns every channel.

For an MSP with O(10) users, O(7) tags, O(20) clients, this is fine. **Plan for cursor-based pagination at Phase 2** before client count exceeds ~100.

### 7.2 N+1 risks

Three patterns stand out:

#### `lib/statistics/queries.ts:142-178` `getEmployeeStats`

```ts
const employees = await prisma.user.findMany({ ... });
const rows = await Promise.all(
  employees.map(async (emp) => {
    const [activeCount, completedCount, hoursAgg] = await Promise.all([
      prisma.job.count({ where: { assignedEmployeeId: emp.id, ... } }),
      prisma.job.count({ where: { assignedEmployeeId: emp.id, ... } }),
      prisma.job.aggregate({ ... }),
    ]);
    return { ... };
  })
);
```

For N employees, this issues 3N queries. With 10 employees, 30 queries. Tolerable today. At 100 employees, 300 queries per stats page load. **Refactor candidate:** single `groupBy` on `Job` with `_count` and `_sum`.

#### `lib/statistics/queries.ts:194-233` `getDepartmentStats`

Same pattern, 3N queries per departments (where N=4 today). Less urgent.

#### `lib/statistics/queries.ts:243-280` `getClientStats`

```ts
const clients = await prisma.client.findMany({ ..., take: 100 });
const rows = await Promise.all(
  clients.map(async (c) => {
    const [activeCount, completedCount] = await Promise.all([
      prisma.job.count({ where: { clientId: c.id, ... } }),
      prisma.job.count({ where: { clientId: c.id, ... } }),
    ]);
    ...
  })
);
```

2N additional queries. At 100 clients, 200 queries per stats load.

#### `lib/dashboard/queries.ts:36-110` `getAdminKpis` / `getAdminDashboardLists`

Returns 50 active jobs and computes `isDelayed` in JavaScript. The SLA-state computation is correctly **not** done in SQL, but the cost is that all `active + has assignedTimestamp` jobs are fetched whenever the admin dashboard loads. With ~50 active jobs this is fine. As volume grows, a cached `slaState` column on `Job` (mentioned in `08-data-model-additions.md` Section 1.1) should land — recompute on transition events. Spec already plans for this.

### 7.3 Missing `select`

A handful of endpoints use `include:` and pull entire related rows when fewer columns would suffice.

- `app/api/clients/[id]/billing/hourly-banks/route.ts:25-27` does `include: { usages: { select: { ... } } }`. Outer level is `include: {}` rather than `select:`, so the full `hourlyBank` row is returned. With 11 columns on `HourlyBank` and a small UI, this is fine.
- `app/api/jobs/[id]/time-sessions/route.ts:18-22` returns the full `TimeSession` row. Acceptable.
- `lib/jobs/queries.ts:67-96` `getJobForUser` uses deep `include` for the detail page. Acceptable.

No critical case found. The `JOB_SELECT` in `lib/jobs/queries.ts:19-43` is exemplary — explicit select shape, sub-relations selected by id and label only. Use this as a template for tightening other endpoints.

### 7.4 Transaction usage

`grep -rn 'prisma.$transaction' app/api lib` returns 33 hits across 31 files. Coverage is excellent. Every mutation that touches more than one row, or that writes an audit log, is wrapped in a transaction. `lib/audit.ts:40` requires the caller to pass `tx` and refuses to write outside one — the type signature enforces it.

Special cases:

- `app/api/hub/[scope]/take/route.ts:24-56` uses a conditional `updateMany` inside the transaction (only update if `status = 'available'`) to safely handle two employees racing to take the same hub job. Correct concurrency design.
- `lib/jobs/numbers.ts:6-24` generates the next public job number with `findFirst({ orderBy: { publicNumber: 'desc' } })` inside a transaction. Comment claims it relies on "serializable-level transaction lock provided by the caller", but no caller actually sets the isolation level. The default Prisma transaction is `READ COMMITTED`, which **does not** prevent two parallel job creates from producing duplicate `publicNumber`. The `unique` constraint on `Job.publicNumber` would catch this with a 5xx error rather than silently failing, so data integrity is preserved, but the user sees a confusing error. **Recommend:** either use `prisma.$transaction(fn, { isolationLevel: 'Serializable' })` or use a sequence (Postgres `nextval`) for public number generation. Same pattern will be needed for `ReceiptDocumentSequence` when Phase 7 lands.
- `app/api/jobs/[id]/time-sessions/route.ts:39-54` ends all active sessions for a user, then creates a new one, inside a transaction. Correct.

### 7.5 Raw queries

`grep -rn '$queryRaw\|$executeRaw'` returns zero hits. The codebase uses only Prisma's typed query builder. Good for safety, but Section 6 will require some raw SQL for partial and GIN indexes.

## 9. Israeli Tax / Receipt Model Correctness

This section flags items that **require accountant or legal verification** before the receipt module is enabled (`receipt_finalize_enabled = false` today).

### 9.1 Document types

`ReceiptDocumentType` enum has 6 values: `invoice`, `receipt`, `tax_invoice`, `tax_invoice_receipt`, `credit_note`, `proforma_invoice`.

Per Israeli Tax Authority (`רשות המסים`) document types under VAT law and the מסמכים ממוכנים standards, these six types broadly align with the standard set. However:

- **Accountant verification needed** on whether the Hebrew/English terminology for each type matches the registered business's tax documents.
- **Allocation number (`mispar hakzaa`)** — the spec includes `allocationNumber`, `allocationStatus`, `allocationObtainedAt`, which aligns with the Tax Authority's allocation-number requirement that began rolling out in 2024 for invoices above a threshold. The data shape is correct. The integration with the Tax Authority API is not implemented; today `allocationStatus` defaults to `not_required`. **This is a known gap requiring real implementation before the receipt module enables.**

### 9.2 VAT calculation

`vatRateBasisPoints Int @default(1800)` represents 18.00%. As of writing, Israel's VAT rate is 18% (raised from 17% on Jan 1, 2025). The default is correct **for invoices issued from Jan 2025 onward**. For credit notes against pre-2025 invoices, the original rate of 17% (1700) must be preserved. The schema supports this (rate is per-row, not global). Good.

Concerns:

- `amountBeforeVat`, `vatAmount`, `totalAmount` are nullable but should be required at finalization. Add a check constraint: when `status = 'finalized'`, all three must be non-null and `totalAmount = amountBeforeVat + vatAmount`.
- No record of who/when the VAT rate was last changed. Acceptable; it is per-row.

### 9.3 Document numbering

The combination of `ReceiptDocumentSequence` (per type, per year) and the composite `@@unique([type, documentNumberYear, documentNumber])` is correct. The Israeli Tax Authority requires document numbers be sequential and gap-less within a series; the current shape supports this but the implementation in Phase 7 must be careful to:

- Use `SELECT ... FOR UPDATE` on the sequence row, not a simple `update` increment.
- Never leave a gap (which means: if a "finalize" fails, do not increment).
- Never re-use a number after a `cancelled` document (cancelled documents must remain in the sequence; a credit note is issued separately).

**The schema supports this. The implementation does not yet exist.** Flag for accountant + Phase 7 review.

### 9.4 Cancellation policy

`ReceiptDocumentStatus` includes `cancelled`. The Israeli convention is that finalized invoices **cannot** be cancelled — only credit-noted. The schema permits a finalized document to transition to cancelled, which is incorrect per tax law for tax-invoice types. The check should be:

- `invoice`, `tax_invoice`, `tax_invoice_receipt`, `receipt`: once `finalized`, only credit-note workflow allowed; status must remain `finalized` forever.
- `proforma_invoice`, `credit_note` (draft): can be `cancelled` freely.

This is application logic (not schema), but flag for the Phase 7 PR.

### 9.5 Currency

`Currency` enum is `ILS`, `USD`, `EUR`. For Israeli tax reporting, foreign-currency invoices must record the exchange rate at issue time. The schema does not have an `exchange_rate` column on `ReceiptDocument` or `Payment`. **Add this before any non-ILS receipt is issued.**

### 9.6 Description lines

`descriptionLines Json @default("[]")` is correct for storing line items. The spec calls for `{description, quantity, unit_price, subtotal}`. No quantity or unit cannot be inferred from `Job`/`HourlyBankUsage` — the receipt is decoupled from the source, which is correct for a snapshot.

**Recommendation for Phase 7:** add a Zod schema or JSON Schema for `descriptionLines` and validate on write.

### 9.7 Items requiring accountant verification

Tabulated for handoff:

| Item | Action |
|---|---|
| Document type Hebrew/English terminology | Accountant sign-off |
| VAT rate default (18%) and historical handling | Accountant sign-off |
| Allocation number integration with Tax Authority API | Implementation needed, then certification |
| Sequence-gap policy on finalize failure | Accountant sign-off |
| Cancellation vs credit-note rules | Accountant sign-off, application logic |
| Exchange rate for non-ILS receipts | Schema addition + accountant sign-off |
| Retention period for finalized documents (7 years implied by tax law) | Add retention column or audit policy |
| Backup integrity for finalized documents | Add to `production-readiness.md` |

## Handoff to PM

**Top 3 data risks before pilot launch:**

1. **No baselined migrations.** `prisma/migrations/` contains only `migration_lock.toml`. The schema has never been recorded as a Prisma migration. Every dev environment, the planned pilot DB, and any future production DB has been (or will be) created via `prisma db push` — which is unsupported for production and offers no rollback path. The Phase 10 audit's claim that `prisma migrate status` is "Up to date" is technically true but misleading; there is nothing to be up to date with. **Before pilot launch, this must be baselined.** Required steps in Section 2.3.

2. **Notification model missing despite being promoted to MVP.** The data-model addendum (`docs/internal-management-portal-enhancement/08-data-model-additions.md` Section 1.5) explicitly promotes `Notification` to MVP and lists three active triggers (`sla.breached`, `job.assigned`, `mention`). The schema has no `Notification` model, no relation on `User`, and no API surface. The Phase 10 hardening audit treats the portal as MVP-complete without flagging this. **PM must reconcile: is Notification still MVP, or has it been silently descoped?** This affects pilot success criteria.

3. **Israeli tax/receipt model needs accountant sign-off before any finalization.** The `receipt_finalize_enabled` feature flag is correctly defaulted to `false`. The schema shape is broadly correct (six document types, VAT rate as basis points, sequence table for atomic numbering). But: (a) no integration with the Israeli Tax Authority allocation-number API exists; (b) finalized documents lack check constraints ensuring `totalAmount = amountBeforeVat + vatAmount`; (c) the schema permits cancellation of finalized tax invoices, which is not legal under Israeli VAT law (credit notes only); (d) no `exchange_rate` column exists for non-ILS receipts. **None of these block the pilot if receipts stay disabled. All of them block enabling receipts.** Coordinate with the accountant well before the planned go-live.
