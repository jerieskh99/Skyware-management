02 · Opportunity

Why this matters now

Skyware's value is the experience the team carries. Today that experience evaporates the moment a job closes. The same problem gets solved twice. Twice the time. Twice the risk of a small mistake.

⏱

Save real time

If 1 in 5 jobs reuses a published lesson, a team of 6 saves around 40 hours/month at conservative estimates. That is the headline business case.

Lower onboarding cost

New employees ramp on a searchable history of "how we actually handled this client" instead of folklore.

Compliance and audit

Documented decisions and verified external references reduce drift and make audit conversations shorter.

Retention

Senior workers stop being the single point of failure. Their lessons live in the system after they take vacation, change roles, or leave.

Sales by demonstration

"Show me how you handle X" becomes a 5-minute walk through a clean knowledge page, not a 30-minute story.

Compounding asset

Unlike features that depreciate, a knowledge base accrues value every quarter we operate.

Nothing about this project is theoretical. The Phase 3 module already has the foundation. The next 15-20 engineering days turn it into a reviewed company memory system.

04 · Vision

Useful company memory, reviewed by humans, supported by automation.

Two flows. Six types. Six statuses. One reviewer queue. Everything else is detail.

What this becomes

  • Reviewed lessons sourced from completed jobs
  • Reviewed external references with verified-on dates
  • A clear reviewer queue your admins can clear daily
  • Type-aware editor that nudges workers toward good structure
  • Optional AI assist that drafts a clean version of a raw writeup
  • Searchable from anywhere in the portal

What this is not

  • Not a customer-facing wiki
  • Not a marketing CMS
  • Not a personal notebook
  • Not the SOP system-of-record for accounting
  • Not a chat archive or paper trail of "notes about people"
  • Not a doc generator that writes by itself

06 · Internal lessons

Task → Knowledge in 5 steps

From a reviewed job to a published lesson. Optional AI assistance. Always a human approval.

1

Job reviewed

Admin marks a completed job as reviewed.

2

Worker drafts

Click "Create knowledge article from this job." Pre-filled with source context.

3

Optional AI assist

One click to structure raw notes into Problem / Cause / Fix / Verification. Worker stays in control.

4

Submit for review

Reviewer queue receives the draft. SLA 5 working days. Same person cannot review own work.

5

Published

Lives in the Knowledge list, global search, and as a cross-link from the source job.

The AI step is optional and runs in dry-run mode for V1. A real LLM call only happens after a separate three-gate verification (flag + env + vendor verified).
07 · External references

A useful link, saved properly.

Not a bookmark dump. A reviewed, tagged, dated reference with a clear reliability tier.

Required fields

  • Source (vendor or publisher name)
  • URL
  • One-paragraph summary
  • Why it matters (when to reach for this)
  • Tags
  • Reliability tier (Verified / Validated / Single source / Anecdotal)
  • Last verified date and verifier

Built-in safeguards

  • Paste the same URL twice = system shows the existing reference
  • Reviewer must approve before publish
  • Weekly link-health check; reviewer notified on rot
  • Freshness pill turns amber after 180 days; never auto-archives
  • Title auto-fetch deferred to V2 behind SSRF guard
08 · Review

Six statuses, nine transitions, one queue.

The reviewer queue is an inbox: Unassigned, Mine, All, Closed. The reviewer decides Approve, Request Changes, or Reject with comment. Approve and Publish are distinct buttons.

States

  • draft
  • ai_structured
  • pending_review
  • approved
  • published
  • archived

Guards

  • Author cannot review own revision
  • Max 2 change-request cycles, then admin arbitrates
  • Approve is reversible; publish opens audit trail
  • Published articles are immutable; edits create new revisions through review

SLAs

  • 5 working days in pending_review triggers a gentle notification
  • If > 30% articles stuck > 7 days, new submissions pause
  • Reviewer dashboard exposes time-to-decision per reviewer
09 · Quality

Quality is engineered, not hoped for.

Editorial rubric + automated checks + freshness sweep + reviewer accountability.

Editorial rubric (reviewer-scored)

  • Clarity 1-5
  • Accuracy 1-5
  • Completeness 1-5
  • Link health 1-5
  • Tag coverage 1-5
  • Type fit 1-5

Threshold: every score ≥ 3 AND sum ≥ 22.

Automated checks on submit

  • Title min length
  • Summary min length
  • Body word floor per type (40-200 words)
  • At least one tag
  • Markdown valid + sanitized (no XSS)
  • Secrets scanner (9 regex patterns)
  • External URL reachable (async HEAD check)
Freshness sweep never auto-publishes or auto-archives. It only notifies a reviewer that an article is overdue for re-verification.

11 · Security

12 threats, mitigated. AI behind 3 gates.

Same proven pattern as the receipts module. Defaults are conservative.

Top mitigations

  • Server-side same-actor guard (no self-review)
  • Secrets scanner warns reviewer
  • Markdown sanitized server-side (allowlist tags + attrs)
  • External URL: no javascript: / data:; rel="noopener"
  • Drafts default to department_only for task lessons
  • Full audit trail on every state change

The three gates for the LLM step

  • 1. Feature flag (default off)
  • 2. Environment variable (unset in dev/staging)
  • 3. Provider verification flag (false until vendor signoff)

Until all three flip, the AI step runs a deterministic dry-run. Worker writeups are never sent to a real model.

V1 ships a complete loop, not a half feature.

A worker can draft, an admin can approve, a reader can find the published result. That is the minimum useful product.

  • 11 new columns + 3 indexes

API and library

  • ~10 new endpoints
  • State machine + same-actor guard
  • AI seam (dry-run only)
  • Secrets scanner
  • Audit on every state change
  • 2 cron jobs: freshness, link health

Interface

  • 4 new pages: list filters, external form, reviewer queue, revisions
  • 17 new components
  • Sanitized Markdown body
  • Task-to-knowledge entry points
  • Hebrew RTL pass
Estimated effort: 15-20 engineering days for one engineer, or 8-10 calendar days with two engineers in parallel (backend + frontend).

14 · Risks

12 risks. Each has a mitigation. Top 3 shape the pilot.

Risks are sorted by likelihood × impact. Mitigations are concrete and tested.

Reviewer queue overflows.
No one has time to review. Articles stale in pending.
High
3-day prod, 5-day escalation, pause submissions if > 30% > 7d.
Secret leak in a published article.
Worker pastes a password or token into a body field.
Medium
Editor regex scanner + reviewer warn + weekly re-scan.
External link rot.
Vendor URLs change or expire.
High
Weekly link-health cron + freshness pill.
Stale articles erode trust.
Workers stop using the system if results are outdated.
High
Per-type stale windows + reliability downgrade on overdue verify.
Markdown XSS via raw HTML.
Author inserts script tags through a permissive renderer.
Medium
Server-side sanitizer with allowlist of tags and attributes.

Deliberately deferred

  • LLM vendor decision. Locked behind the 3-gate posture until V2.
  • Customer-facing subset. Far-future; requires separate compliance review.
  • Semantic search. Augments FTS in V3, does not replace it.
  • Multi-language bodies. Hebrew RTL works in V1; full he/en/ar parallel content is V3.
