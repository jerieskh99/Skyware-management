Current state summary

Skyware Internal Management Portal MVP. Audited 2026-05-24.

01 / 10

The portal is functionally substantial and architecturally consistent. It ships with 22 server pages, 38 API routes, 52 components, and a 35-model Prisma schema. The team has been disciplined: zero TODO, FIXME, console.log, or as any markers in app/ or components/.

What works well

  • Uniform API shape. Every mutation goes auth then role gate then Zod then transaction with audit. Every sampled route follows it.
  • Coherent route group layout under (auth), (portal), api.
  • Shared primitives. PageHeader, KpiCard, SectionCard, EmptyState, plus job-domain reusables, give the app a consistent visual vocabulary.
  • Audit log on every mutation. Transaction-only enforcement via writeAudit.
  • Honest placeholders. Receipts, Agent, Financial Documents pages are well-built stubs gated by feature flags.
Verdict: the MVP skeleton is sound. The improvement work is about operational plumbing, UX polish, missing migrations, missing tests, and a small set of analytics fixes. The product concept stays.

Product and UX improvement direction

Keep the concept. Sharpen the surface.

03 / 10

Principles

  • Bilingual by default. Hebrew renders translated text, not just RTL layout.
  • Safe-by-default mutations. No silent destructive action.
  • Visible feedback. Loading skeletons, toast on every success, notification bell.
  • Honest analytics. Metric tooltips, deterministic computations, self-view for employees.
  • Faster pages. No N+1, FTS indexes, single aggregated queries.

Surface changes that ship

  • Radix Dialog replaces bespoke overlays.
  • ConfirmDialog for irreversible deletes.
  • Global toast surface for cross-page feedback.
  • Notification bell in header with three triggers.
  • Saved views on Jobs, Clients, Billing.
  • Time-bucketed aging strip on billing and dashboard.
  • Hourly-bank burn-rate bar on client card.
  • /statistics/me employee self-view with tooltips.
  • Job detail tabs and reassign control.

Strengths to preserve

The shared primitive layer (PageHeader, KpiCard, SectionCard, EmptyState, JobStatusChip, JobPriorityChip, JobSeverityChip, JobTagChips, JobSlaBar, JobRow) stays. Replicate the pattern for billing and clients (a PaymentStatusChip already exists, a ClientStatusBadge would close the duplication).

Backend, frontend, and database plan

What changes in each layer and why.

04 / 10

Backend API + Ops

Goal: reliable, observable, deduplicated.

  • Apply uniform API shape to every new route.
  • Centralize duplicated job-scope permission filter.
  • Real database ping on /api/health; return 503 on failure.
  • Add lib/logger.ts and pipe API catches through it.
  • Rate-limit NextAuth credentials endpoint and admin password reset.
  • Return JSON 401 from /api/* instead of redirecting to /login HTML.
  • Split app/(portal)/admin/page.tsx into per-tab files.

Frontend UI + UX

Goal: safe, feedback-rich, bilingual.

  • Wire lib/i18n/ to every visible string.
  • Replace eight bespoke modals with Radix Dialog.
  • Add ConfirmDialog to destructive deletes.
  • Global toast surface; remove inline "Saved." patterns.
  • Per-domain loading.tsx and Suspense boundaries.
  • Notification bell with last-10 dropdown and read state.
  • Saved views UI on Jobs, Clients, Billing.
  • Job detail tabs (Overview, Timeline, Related, Files) and reassign control.
  • Time-bucketed aging strip and hourly-bank burn-rate bar.

Database Schema + Queries

Goal: reproducible, indexed, deployable.

  • Generate a baseline migration from current schema and mark applied on existing dev DBs.
  • Switch the team workflow from db push to migrate dev.
  • Add the Notification model and three triggers.
  • Add partial unique index on Client.israeli_tax_id.
  • Add partial index on TimeSession(user_id) WHERE ended_at IS NULL.
  • Add pg_trgm indexes on Job and CommunicationPost text fields.
  • Rewrite N+1 statistics and dashboard queries as single aggregated queries.
  • Document deletion semantics for relations that default to RESTRICT.

Preserved MVP functionality

The core skeleton stays. Nothing here is removed.

  • Three employee groups: Helpdesk, IT, R&D.
  • Two admin roles: CEO, CTO.

Communication

Clients

  • Billing tab combining all billing categories.

Billing and payments

  • Three categories: Monthly, Hourly Bank, One-Time Job.
  • Payment status workflow.
  • Mark-paid handoff with create-receipt step.
  • Aging list (buckets added in Phase 2).

Receipts and Tax

  • Schema-ready, six document types.
  • Finalization gated by receipt_finalize_enabled.
  • Accountant sign-off required before enabling.

Admin

  • Users, tags, feature flags, audit log.
  • Roles and departments.
  • SLA and Company Details tabs (storage in Phase 3).
Preservation rule: when in doubt, keep. Every audit ranked rearrange and improve above remove.

Phased roadmap

Three phases, each gated by an exit checklist.

07 / 10

Phase 1 Pre-pilot hardening

2 weeks. Blocks pilot launch.

  • Baseline migration + Notification model + indexes.
  • CI workflow; fix broken e2e; add P0 contract tests.
  • Real /api/health; rate-limit auth; JSON 401.
  • Radix modals; ConfirmDialog; remove window.alert.
  • Toast surface; wire i18n; fix two wrong metrics.

Phase 2 Pilot polish

3 weeks. Runs during the first half of the pilot.

  • Notification bell with three triggers; settings prefs.
  • Saved views on Jobs, Clients, Billing.
  • Aging buckets; hourly-bank burn; admin dashboard strips.
  • Employee self-view + tooltips on every KPI.
  • Job detail tabs and reassign control.
  • Skeleton loaders and toast feedback everywhere.
  • FTS indexes; global search with scope chips.
  • N+1 fixes in statistics and dashboard.

Phase 3 Post-pilot expansion

4-6 weeks. Driven by pilot feedback.

  • SLA DB-backed defaults + breach automation.
  • Company Details storage and edit UI.
  • File attachments on jobs, posts, replies.
  • Receipt finalization (after accountant sign-off).
  • Recurring job templates.
  • Knowledge articles.
  • Client health snapshots.
  • Saved views team-shared.
Resourcing: 2 engineers half-time finishes Phase 1 in two weeks and starts Phase 2 in parallel. Cuts list in implementation_plan.md Section 7 if only one engineer is available.

Risks and tradeoffs

Each risk has a mitigation. Top three are pilot-blocking.

08 / 10
#RiskLikelihoodImpactMitigation
R1Baseline migration breaks dev DBsMediumHighStop schema edits; migrate diff from empty; migrate resolve --applied on existing DBs
R2i18n wire-up causes missing-key crashes in HebrewMediumMediumFallback to English; lint script comparing en.json and he.json keys
R3Notifications scope creep delays pilotHighMediumCap scope to three triggers in 08-spec; bell + dropdown only
R4CI flakes block workMediumLowAllow re-run; e2e non-blocking initially; promote after one stable week
R5N+1 rewrite changes metric numbersMediumMediumSnapshot pre-rewrite values; reconcile new queries against snapshot
R6Toast system adds visual noiseLowLowLimit toasts to mutation success/error; not navigation
R7Destructive-action confirms slow expert usersLowLowSingle-step confirms; typed item name only on irreversible deletes
R8Pressure to enable receipt finalization earlyLowHighKeep flag off until accountant sign-off; documented in pilot checklist
R9Role-targeted flags accidentally make features admin-onlyLowMediumAdd tests that flag-off behavior matches the pre-flag baseline
R10Phasing slows a small team that wants to shipMediumLowUse phasing taxonomy only for mutations, money, auth changes

Top three tradeoffs

  • Migration discipline vs. velocity. Moving from db push to migrate dev adds friction. The rollout safety benefit is the largest single risk-reducer in this plan.
  • Notifications scope vs. pilot date. A full notifications platform is multi-week work. The plan ships bell + three triggers; preferences UI; nothing else.
  • Analytics correctness vs. surface area. Phase 2 fixes the two wrong metrics and adds tooltips. Phase 2 does not ship every spec metric. Aging buckets and burn-rate are in; some deeper analytics (revenue per employee, MRR mix) wait for a confirmed Payment-amount semantics review.

Definition of done

Per item and per phase. Used by reviewers and by the PM.

09 / 10

Per item

  1. Code merged behind a feature flag (where the change class needs one).
  2. Migration committed and applied to staging.
  3. Unit or contract test added for the new logic.
  4. Translations added to en.json and he.json.
  5. Manual RTL pass passed for new screens.
  6. Admin ring enabled for at least 48 hours without issue reports.
  7. Full rollout flag turned on.
  8. Flag marked retired after two weeks of full rollout.

Per phase

Phase 1 exit

  • Baseline migration + Notification model in prisma/migrations/.
  • CI runs on every PR; lint, typecheck, unit green.
  • E2E green at HEAD.
  • /api/health returns 503 on Postgres failure.
  • No bespoke modal remains; no window.alert.
  • Hebrew renders translated text on every page.
  • Two wrong metrics fixed or renamed.

Phase 2 exit

  • Notification bell live; saved views available; aging buckets visible.
  • Burn-rate bar on client card; admin dashboard strips updated.
  • /statistics/me live with metric tooltips.
  • Job detail tabs and reassign live.
  • Statistics page p95 under 1.5 s at 50 employees.
  • FTS indexes deployed; global search with scope chips.

Phase 3 exit

  • SLA defaults editable; breaches notify.
  • Company details stored and editable.
  • Attachments live on jobs, posts, replies.
  • Receipts either enabled with accountant sign-off or formally deferred.
  • Recurring templates and knowledge articles live.
  • Client health snapshots available on client detail.
