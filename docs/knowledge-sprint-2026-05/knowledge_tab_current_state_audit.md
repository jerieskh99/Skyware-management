# Knowledge tab: current state audit

## 1. Summary

The Knowledge module shipped in Phase 3 Workstream 5.6 as a thin CRUD surface for
internal articles. It owns one model (`KnowledgeArticle`) plus a join table
(`KnowledgeArticleTag`) that reuses the existing `Tag` registry. The product
shape is "an admin writes a draft, publishes it, employees can read internal
published articles." There is no review workflow, no AI-assisted ingestion, no
linkage to jobs or task completion, no external-reference type, and no
reliability metadata. The whole surface is gated by the
`knowledge_articles_enabled` feature flag, which defaults to `false` in the
fixtures and is currently off. A second feature flag (`fts_search_enabled`)
gates the cross-cutting `/search` page that exposes the knowledge bucket. The
task-completion flow (Mark done -> work report -> done -> reviewed) has zero
integration with knowledge today; nothing in the work-report path writes to or
prompts about a knowledge article.

Indexes (from migration lines 38-45 plus FTS migration 20260524001150):

- `knowledge_articles_pkey` on `(id)` (PK).
- `knowledge_articles_slug_key` UNIQUE on `(slug)`.
- `knowledge_articles_status_updated_at_idx` on `(status, updated_at DESC)`.
- `knowledge_articles_related_client_id_idx` on `(related_client_id)`.
- `knowledge_articles_title_trgm_idx` GIN trigram on `(title)` (FTS migration).
- `knowledge_articles_body_trgm_idx` GIN trigram on `(body)` (FTS migration).

Note: the trigram migration relies on `pg_trgm` already being enabled by an
earlier migration (`20260524000200_fts_trigram_indexes`, referenced in the
comment on line 2 of the FTS migration).

There is NO trigram index on `summary`, even though
`searchKnowledge` and `listArticles` both filter on `summary` with
`contains, mode: "insensitive"` (`lib/search/queries.ts` line 267,
`lib/knowledge/queries.ts` line 82).

### 2.3 `KnowledgeArticleTag` (table `knowledge_article_tags`)

Schema source: `prisma/schema.prisma` lines 1076-1085.
Migration source: `prisma/migrations/20260524001100_knowledge_articles/migration.sql` lines 30-36, 57-60.

| Field       | Type   | Nullable | Default | FK / Notes |
|-------------|--------|----------|---------|------------|
| `articleId` | `UUID` | no       | none    | FK -> `knowledge_articles(id)` `ON DELETE CASCADE ON UPDATE CASCADE`. |
| `tagId`     | `UUID` | no       | none    | FK -> `tags(id)` `ON DELETE CASCADE ON UPDATE CASCADE`. |

Constraints:

- Composite PK on `(articleId, tagId)` (`@@id([articleId, tagId])`).
- No additional indexes beyond the PK.

The schema reuses the global `Tag` model (`schema.prisma` lines 401-418). `Tag`
has a `scope` field with values `communication | job | both`
(`enum TagScope` lines 127-131). The schema comment at line 1074-1075 says only
`communication`, `job`, or `both`-scoped tags should attach to articles, but
this is not enforced in the database or in `attachTag` in
`lib/knowledge/queries.ts` (no scope check). The API endpoint
`POST /api/knowledge/[slug]/tags` confirms the tag exists by id but does not
inspect its `scope` (lines 37-42 of `app/api/knowledge/[slug]/tags/route.ts`).

## 3. API surface

All endpoints are gated by `getFeatureFlag("knowledge_articles_enabled")`. When
the flag is off every endpoint returns 404 (`notFound("Knowledge articles")`).
Auth is checked via `requireAuth()`; admin checks via `isAdmin(auth.user)`.
Admin = `user.isAdmin === true`, derived from role keys `ceo` or `cto`
(`lib/permissions.ts` lines 14-16 and elsewhere).

### `GET /api/knowledge`

File: `app/api/knowledge/route.ts` lines 24-60.

- Auth: any logged-in user.
- Flag gate: required.
- Query Zod schema (`listQuerySchema`, lines 16-22):
  - `status?: 'draft'|'published'|'archived'`
  - `q?: string` (trimmed, max 200)
  - `tag?: string` (trimmed, max 80; matches `Tag.key`)
  - `limit?: number` (positive int, max 100)
  - `cursor?: string` (min 1; id-based, gt cursor)
- Non-admin behavior: status is force-set to `published` and the underlying
  `listArticles` query applies `visibility = 'internal'`.
- Admin behavior: passes `status` through; default is "non-archived"
  (`lib/knowledge/queries.ts` lines 70-78).

### `POST /api/knowledge`

File: `app/api/knowledge/route.ts` lines 70-97.

- Auth: admin only (`isAdmin` gate).
- Body Zod schema (`createBodySchema`, lines 62-68):
  - `title: string` trimmed, 1..200 chars.
  - `body: string` trimmed, 1..50000 chars.
  - `summary?: string` trimmed, max 400.
  - `visibility?: 'internal'|'admin_only'` (default `internal`).
  - `relatedClientId?: UUID`.
- Creates row with status `draft`; audit action `knowledge.created`.

### `GET /api/knowledge/[slug]`

File: `app/api/knowledge/[slug]/route.ts` lines 20-32.

- Auth: any logged-in user.
- Flag gate: required.
- Calls `getArticleBySlug(slug, isAdmin)`. Non-admins do not see
  `admin_only` rows nor non-`published` rows (`lib/knowledge/queries.ts`
  lines 112-115). Returns 404 in both cases.

### `PATCH /api/knowledge/[slug]`

File: `app/api/knowledge/[slug]/route.ts` lines 34-76.

- Auth: admin only.
- Body Zod schema (`patchSchema`, lines 34-41):
  - `title?` 1..200.
  - `body?` 1..50000.
  - `summary?: string|null` max 400.
  - `visibility?: 'internal'|'admin_only'`.
  - `relatedClientId?: UUID|null`.
  - `regenerateSlug?: boolean` (default false; slug stays stable on title
    change unless explicitly true).
- Audit action `knowledge.updated`; only fields that changed appear in diff.

### `DELETE /api/knowledge/[slug]`

File: `app/api/knowledge/[slug]/route.ts` lines 78-103.

- Auth: admin only.
- Hard delete via `deleteArticle` in `lib/knowledge/queries.ts` lines 364-384.
- Audit action `knowledge.deleted`.

### `POST /api/knowledge/[slug]/publish`

File: `app/api/knowledge/[slug]/publish/route.ts`.

- Auth: admin only.
- No request body.
- Sets `status='published'` and `publishedAt = existing.publishedAt ?? new Date()`
  (i.e., earliest publication wins on re-publish). Audit action
  `knowledge.published`.

### `POST /api/knowledge/[slug]/archive`

File: `app/api/knowledge/[slug]/archive/route.ts`.

- Auth: admin only.
- No body. Sets `status='archived'`. Audit action `knowledge.archived`.
- Archived rows drop out of `listArticles` for non-admins (filter
  `status: { not: "archived" }` only applies when admin omits status; non-admins
  are pinned to `published`) and out of `searchKnowledge` (which is pinned to
  `status: "published"`).

### `POST /api/knowledge/[slug]/tags`

File: `app/api/knowledge/[slug]/tags/route.ts` lines 13-51.

- Auth: admin only.
- Body Zod schema: `{ tagId: UUID }`.
- Looks up the article by slug and the tag by id. 404 if either is missing.
- Upserts the join row via `attachTag` in `lib/knowledge/queries.ts` lines
  386-402. Audit action `knowledge.tag_attached`.

### `DELETE /api/knowledge/[slug]/tags`

File: `app/api/knowledge/[slug]/tags/route.ts` lines 53-89.

- Auth: admin only.
- Accepts `tagId` either as a query param `?tagId=` (preferred by the
  `ArticleTagPicker` client) or as a JSON body field. Audit action
  `knowledge.tag_detached`.

### Endpoints that do NOT exist (relevant to the sprint)

- No "unpublish" endpoint, even though `unpublishArticle` exists in
  `lib/knowledge/queries.ts` lines 336-362 and is unused.
- No review/approval endpoint or status (e.g., `in_review`).
- No "create article from job" or "create article from work report" endpoint.
- No bulk endpoints (bulk delete, bulk tag).
- No revision history endpoint; updates overwrite in place.
- No external-reference type and no URL list endpoint.

## 5. Search integration

### 5.1 Search bucket

File: `lib/search/queries.ts` lines 52-59, 241-307.

- `SearchScope = "all" | "jobs" | "clients" | "posts" | "knowledge"` (line 12).
- `KnowledgeHit` returns `{id, slug, title, summary, visibility, updatedAt}`.
- `searchKnowledge(user, q, opts)` lines 241-284:
  - Requires `q.length >= MIN_QUERY_LENGTH (2)`.
  - Always filters `status: "published"`.
  - Adds `visibility: "internal"` when `!isAdmin(user)`.
  - Cursor-paginates by `id > opts.cursor`.
  - OR-matches `title`, `body`, `summary` via `contains, mode: "insensitive"`.
    These rely on the trigram GIN indexes for title/body and a sequential scan
    for summary.
  - Default page size = `DEFAULT_LIMIT (20)`, capped at `MAX_LIMIT (50)`.
- `searchAll(user, q, options)` lines 286-307: takes
  `{includeKnowledge?: boolean}`. When false (the default), the knowledge
  bucket is short-circuited to an empty page and no DB call is made. The page
  size in the "all" mode is `ALL_SCOPE_PER_BUCKET (5)`.

### 5.2 Search route

File: `app/api/search/route.ts`.

- Zod scope enum includes `"knowledge"` (line 19).
- `scope=knowledge` with the flag off returns 403 "Knowledge search is
  disabled." (lines 49-52).
- `scope=all` with the flag off omits the `knowledge` key from the response
  payload (lines 57-65) -- it does not simply zero the bucket; the key is
  stripped.

### 5.3 Search UI

File: `app/(portal)/search/page.tsx`.

- Reads both `fts_search_enabled` and `knowledge_articles_enabled` flags
  (line 50).
- If `fts_search_enabled` is off: `notFound()` (page disappears entirely).
- If `scope=knowledge` is requested but the knowledge flag is off, the page
  silently coerces scope to `"all"` (line 66).
- Knowledge bucket rendered as a `SectionCard` with `BookOpen` icon (lines
  291-335). Cursor-based "Load more" link is wired.

### 5.4 Visibility gate (cross-bucket)

For non-admins, knowledge hits are always `visibility=internal` and
`status=published`. For admins, both visibilities are returned but `status` is
still pinned to `published`. There is no way to search drafts via the public
search endpoint. The `listArticles` query is the only path that exposes drafts
to admins, via the list page chips.

## 7. Task workflow today

This is the integration point for the future "task to knowledge" feature. The
flow exists today entirely separately from knowledge.

### 7.1 Status enum

`prisma/schema.prisma` lines 30-41:

```
enum JobStatus {
  new
  assigned
  available
  taken
  working_on_it
  waiting_for_client
  waiting_for_admin
  done
  reviewed
  cancelled
}
```

### 7.2 Lifecycle table

`lib/jobs/lifecycle.ts` lines 11-60 defines the canonical transition table.
The relevant tail is:

- `working_on_it -> done`: allowed for `admin` or `assignee`.
- `done -> reviewed`: allowed for `admin` only.
- `done -> working_on_it` (reopen): allowed for `admin` or `assignee`.
- `reviewed -> working_on_it` (reopen): admin only.
- `reviewed` has no other outgoing transitions; `cancelled` is terminal.

### 7.3 End-to-end happy path

1. **Admin creates a job** (`app/api/jobs/`); status is typically `new` or
   `assigned`.
2. **Job appears on `/my-jobs`** (`app/(portal)/my-jobs/page.tsx`). Click
   through to detail.
3. **Detail page** (`app/(portal)/my-jobs/[id]/page.tsx`). Two layouts gated
   by `job_detail_tabs_enabled`: legacy single-column (description, optional
   work-summary block, timeline, actions) or tabbed
   (`Overview | Timeline | Related | Files`) rendered by
   `components/jobs/Job{Overview,Timeline,Related,Files}Tab.tsx`.
4. **Status transitions** via `<JobTransitionButtons>`
   (`components/jobs/JobTransitionButtons.tsx`): "Start working" (line
   100-104), "Mark done" opens `<MarkDoneSheet>` (line 113-117), waiting
   for client/admin and resume (lines 119-135), "Mark reviewed" admin-only
   (line 137-139), "Reopen" admin-only (line 141-143), "Cancel" admin-only
   (line 145-147). All non-Done transitions POST to
   `/api/jobs/[id]/transitions` with `{toStatus, note}` (file
   `app/api/jobs/[id]/transitions/route.ts`); the schema also accepts
   `assignedEmployeeId` for `toStatus="assigned"`.
5. **Mark done** (`components/jobs/MarkDoneSheet.tsx`) takes `summary`
   (required), `totalTimeMinutes` (defaults to running timer total), and
   `billable` (default true). Submits to `/api/jobs/[id]/work-report` (line
   40-44). The handler at `app/api/jobs/[id]/work-report/route.ts`:
   - Requires assignee or admin (lines 27-29).
   - Requires status in `working_on_it`, `waiting_for_client`, or
     `waiting_for_admin` (lines 32-37).
   - In a transaction (lines 43-97): upserts `WorkReport` (one per job
     by `jobId @unique`); updates Job to `status='done'`,
     `timeSpentMinutes`, `completedTimestamp=now`; writes a `JobStatusEvent`
     with the time delta; calls `writeAudit` with action
     `job.work_report_submitted`.
6. **Reviewed.** Admin clicks "Mark reviewed" -- the generic
   `/api/jobs/[id]/transitions` route stamps `reviewedTimestamp` (line 55).
   No knowledge prompt, no review-of-content step.

### 7.4 Where knowledge could attach

The work-report path is the natural fork between "summary exists" and "job
closed." Today nothing in `work-report/route.ts`, `transitions/route.ts`,
`MarkDoneSheet.tsx`, `JobTransitionButtons.tsx`, `JobOverviewTab.tsx`, or
`JobRelatedTab.tsx` references knowledge. `JobRelatedTab.tsx` lists
`linkedPayment` and `relatedPosts` only. `WorkReport` has no FK to
`KnowledgeArticle`; no `sourceJobId`/`sourceWorkReportId` exists on the
article side either.

## 9. Gaps versus the stated goal

The stated goal is "reviewed internal lessons + external references." Today the
module supports only the first half, and only partially. Concrete gaps with
file evidence:

- **No review workflow.** Status enum is `draft | published | archived` only
  (`prisma/schema.prisma` lines 1029-1033). No `in_review`, `needs_changes`,
  or `approved` state. `publishArticle` (`lib/knowledge/queries.ts` lines
  279-306) only checks `isAdmin`; one admin can author, publish, and own the
  audit trail. `WorkReport` has `approvedById`/`approvedAt`
  (`schema.prisma` lines 367-368), but `KnowledgeArticle` does not.
- **No external-reference type.** `KnowledgeArticle` has no `url`, `source`,
  `referenceType`, or related column (verified in `schema.prisma` lines
  1042-1067 and the migration). Cannot record "this is a link to vendor docs"
  as a knowledge entry.
- **No reliability/verification metadata.** No `verifiedAt`,
  `verifiedByUserId`, `nextReviewDueAt`, `staleAfterDays`, `confidence`, or
  `severity`. List/search ordering is `updatedAt DESC` only
  (`lib/knowledge/queries.ts` line 95).
- **No AI structuring.** No prompt path, no LLM call. Editor body is a plain
  `<Textarea>` (`components/knowledge/ArticleEditor.tsx` line 109). Body is
  one free-text TEXT column; no JSON-Schema structured representation.
- **No task-to-knowledge integration.** `WorkReport` (`schema.prisma`
  359-378) has no FK to `KnowledgeArticle`. `app/api/jobs/[id]/work-report/route.ts`
  writes nothing to knowledge. `MarkDoneSheet.tsx` and `JobRelatedTab.tsx`
  have no article affordance.
- **No body rendering.** Detail page (`app/(portal)/knowledge/[slug]/page.tsx`
  lines 83-85) wraps `article.body` in `<pre>`. Markdown features render as
  literal text despite the schema comment at `schema.prisma` line 1047
  claiming "Markdown body."
- **No revision history.** Updates overwrite in place
  (`lib/knowledge/queries.ts` `updateArticle` lines 202-277). Audit log body
  diffs are `(omitted)`/`(updated)` placeholders (line 235). No way to view
  what the article said two weeks ago.
- **No tag-scope enforcement.** Schema comment at lines 1074-1075 implies
  scope matters; attach endpoint (`app/api/knowledge/[slug]/tags/route.ts`
  lines 37-42) checks existence only; picker shows every tag from `/api/tags`.
- **No related-article relations.** No self-join, no `Job -> Article[]`, no
  `CommunicationPost -> Article[]`.
- **No content size or attachment story.** Body capped at 50000 chars
  (`createBodySchema` line 64). Knowledge has no attachment integration
  despite the `attachments_enabled` flag existing for Jobs/Posts/Replies. No
  inline image hosting.
- **No "owner" beyond create-time stamp.** `authorUserId` is set once and
  never changes; no ownership-transfer path. `lastEditedByUserId` does track
  publish/archive (helpers connect it at lines 294, 322, 349 in
  `lib/knowledge/queries.ts`).
- **No notifications on knowledge events.** `NotificationKind` (referenced
  from `schema.prisma` near line 903) is not extended with knowledge events;
  nothing notifies on publish/archive/review-due.

## 10. Risks the planning team should know about

1. **Hard delete in production.** `DELETE /api/knowledge/[slug]`
   (`app/api/knowledge/[slug]/route.ts` lines 78-103) calls
   `tx.knowledgeArticle.delete`. Audit captures `title`/`slug` but the body
   is gone. Any review workflow must decide whether to keep this.
2. **Single-actor publish.** Same admin can author, publish, and own the
   audit trail. Combined with hard delete, an admin can produce, publish, and
   erase content with no second pair of eyes.
3. **Plain-text rendering masquerading as Markdown.** Body comment says
   "Markdown" but the detail page renders inside `<pre>`. Any future Markdown
   pipeline must ship with HTML sanitization (XSS risk on raw HTML).
4. **No FTS index on `summary`.** `searchKnowledge` queries `title`, `body`,
   `summary` (`lib/search/queries.ts` lines 263-269) but the FTS migration
   only indexes `title` and `body`. Summary search degrades to sequential
   scan.
5. **Cursor pagination uses `id > cursor` with `updatedAt DESC` ordering**
   (`lib/knowledge/queries.ts` lines 88-90, 92-97 and `lib/search/queries.ts`
   lines 248-250). Cursor relies on secondary `id` order; on `updatedAt` ties
   the cursor could skip or repeat rows.
6. **`Tag.scope` ignored on attach.** Schema comment (lines 1074-1075) implies
   scope matters; the attach endpoint checks existence only. Any future
   scope-driven UX must migrate existing data.
7. **No fixture data on flag flip.** Fixtures directory has `roles.json`,
   `feature-flags.json`, `channels.json`, `departments.json`, `tags.json` but
   no `knowledge_articles.json`. First enable lands on an empty table with
   only the "Admins can write the first one" copy as onboarding.
8. **`relatedClientId` is the only structured link.** No FK from
   `KnowledgeArticle` to `Job`, `WorkReport`, `CommunicationPost`, or
   `Department`. Any task-to-knowledge feature must add at least one new
   column or join table.
9. **Audit body diffs are placeholders.** `lib/knowledge/queries.ts` line 235
   writes `{old: "(omitted)", new: "(updated)"}` for body changes. Reviewers
   cannot answer "what changed?" from the audit log alone.
10. **Audit visibility on create reports `null -> internal`.** Lines 175-181
    of `lib/knowledge/queries.ts` write `{old: null, new: row.visibility}`
    even when the client never sent a value (default applied). Noisy for
    "who changed visibility?" triage.
11. **Re-publish stamp is earliest-wins.** `publishArticle` line 293 uses
    `existing.publishedAt ?? new Date()`. An article archived and later
    re-published keeps its first `publishedAt`. May hide that the article was
    offline.
12. **No rate limiting on list or search.** Any authenticated user can hammer
    `GET /api/knowledge` and `GET /api/search`. Trigram ILIKE is cheap today;
    a future Markdown render pipeline on read could become expensive.
